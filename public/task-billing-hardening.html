Stream A

Billing correctness & tenant isolation

Tighten the invariants the rest of the product rests on. No new features.

fix/billing-hardening
  1. A1

    Close the idempotency TOCTOU race

    P0

    Today the debit route checks "any DEBIT row already for this resourceId?" as a SELECT before calling atomic_debit(), outside the advisory lock. Two concurrent identical-resourceId debits can both pass the pre-check and both charge.

    • Locate which table stores resource_id for DEBIT rows (likely wallet_transactions and/or usage_events).
    • Add a new migration 0003_idempotency_constraint.sql (never edit 0001/0002 in place) that adds a UNIQUE constraint or partial unique index enforcing one DEBIT per (workspace_id, resource_id).
    • Move idempotency enforcement inside the atomic_debit() transaction: attempt the insert, catch the unique-violation, and on conflict return the existing balance with idempotent: true instead of charging again.
    • Keep the existing pre-SELECT only as an optional fast path; the DB constraint must be the authoritative guard.
    • Confirm whether resourceId or idempotencyKey is the real idempotency key - the docs are ambiguous. Pick one, make it authoritative, and note the decision in ARCHITECTURE.md §6.
    Acceptance: fire 20 parallel debits with the same resourceId → exactly one charge, 19 idempotent hits, balance debited once, never negative.
  2. A2

    Tenant isolation is app-layer only

    P0

    Everything runs as service-role and bypasses RLS, so isolation rests entirely on the workspace.tenant_id == key.tenantId check in route code. One missing check = cross-tenant money/data leak, and there's no test catching it.

    • First, add an automated regression test proving isolation: a key from tenant A must get 403 on authorize, debit, and read against a tenant-B workspace. Do this regardless of the rest - it's the highest-leverage, lowest-risk step.
    • Then propose (DO NOT implement yet) a DB-level defense-in-depth option:
      • An assertion inside the atomic_debit/authorize RPC that the caller-supplied tenant_id matches the workspace's tenant_id, OR
      • Real RLS policies keyed off a per-request set_config('request.tenant_id', …) GUC.
    • Show me the trade-offs (perf, complexity, migration risk) and wait for my pick before changing the schema or auth path.
  3. A3

    Document two known design gaps

    Docs

    Add a short "Known billing gaps" subsection to docs/ARCHITECTURE.md. Don't fix - just document:

    • "Ran but couldn't bill" race: authorize passes → agent runs → a concurrent debit drains the balance → this debit 402s after the work is already done = unbilled work. Idempotency doesn't cover this. Note a reservation/hold pattern as the future fix.
    • authorize() is on the hot path: a synchronous remote hop on every action. Note client-side entitlement caching as a future optimization.
  4. A4

    Session cookie flags

    P1

    Verify both session cookies (agentmint_session, agentmint_builder_session) set HttpOnly, Secure in production, and SameSite. Add if missing. Confirm there's a session expiry. Don't change the HMAC scheme.

Stream B

Landing page honesty

Edit public/landing.html + the design/landing.html mirror + the React app/page.tsx if it duplicates this copy. Touch copy/claims and stats only - do not change the visual design, color system, layout, or animations.

fix/landing-claims
  1. B1

    Stats band is fabricated

    P0

    The hard numbers in the stats band are fabricated for a pre-pilot product: 1,248,903 credits authorized · 47ms p99 · 6 live agents in production · 99.99% atomic debit accuracy. Either:

    • Delete the stats band, or
    • Replace with honest framing (capability statements, or numbers explicitly labelled "illustrative").

    Do not present invented metrics as real. Same goes for the "31% trial → paid" funnel - mark it illustrative or remove.

  2. B2

    "99.99% atomic debit accuracy" is a category error

    P1

    Atomicity isn't a percentage - it's a correctness property. Reframe as the actual guarantee: balance never goes negative, idempotent by resource_id, append-only ledger.

  3. B3

    Reconcile claims with what's actually built

    P0

    Anything that depends on stubbed/unbuilt features must either be marked as roadmap or softened to what's real today:

    • "Money landing in your bank" / Stripe Connect → roadmap.
    • "Real-time MRR & NRR" → roadmap (revenue page only shows recent calls right now).
    • "Branded for your product, hosted by us" → roadmap (no per-tenant branding yet).

    Keep the existing "Team seats (Phase 2)"-style honest labeling pattern.

  4. B4

    Reframe the "30 minutes" promise

    P1

    "30 minutes" should describe instrumenting billing, not money-in-your-bank. Stripe Connect onboarding isn't 30 minutes and is stubbed. Keep the line punchy, but accurate to what 30 minutes actually buys.

  5. B5

    Surface AgentMint's own pricing higher than the FAQ

    P1

    A self-serve dev audience wants to know what they'll pay before scrolling to FAQ. Keep the framing: first cohort = $0, then a platform fee + a capped percentage of payment volume.

  6. B6

    Fix the "SDK" naming

    P1

    There is no SDK package. It's two HTTP calls. Either say "two HTTP calls" consistently, or clearly note the SDK is a thin wrapper that's coming.

  7. B7

    402 example mixes two distinct rejection shapes

    P1

    The on-page 402 example uses reason: "insufficient_credits" but includes requiredPlan and shortfall - that muddles the two distinct rejection shapes (INSUFFICIENT_CREDITS vs PLAN_INSUFFICIENT) from ARCHITECTURE.md §11.5. Make the example match exactly one of the real shapes.
